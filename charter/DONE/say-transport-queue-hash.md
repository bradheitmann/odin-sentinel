Problem (all three seen on a live multi-seat run on 2026-11-10):
- A send that the terminal multiplexer itself refused was recorded as INPUT_BAR_ONLY with note send-failed. That state claims the text sits in the input bar; the pane's bar was empty. The multiplexer's exit status and error text are discarded, so the cause is on no record.
- Claude Code queues a message typed while it is mid-turn: the text appears on a prompt line and the input bar shows `Press up to edit queued messages`. The sender refuses a busy Claude Code pane after the wait budget; a consumer's shell sender read 26 such queued sends as stuck text in one hour. Only Pi is treated as queueing today, because only Pi had a real capture.
- A proof record names the surface and the time but not which message. A board stamp checked against it proves that something was delivered, not what.
Design (fixed for this slice):
- A. Transport failure. New delivery state `SEND_FAILED`. When the multiplexer's send-text command fails (non-zero exit, killed by a signal, or the binary cannot be run), the sender types nothing further, exits 5 as today, and writes one `send_refusal` record with state SEND_FAILED, submitted false, note `send-failed`, and a new field `transport_error`: the multiplexer's exit description followed by the first line of its error output, on one line, at most 300 characters. When the text was sent but the Enter key command fails, the state stays INPUT_BAR_ONLY (the text is in the bar), the note is `enter-failed`, the exit is 5, and `transport_error` is set the same way. `transport_error` is null on every other record.
- B. Claude Code queues. In pane-rules.json the claude-code harness moves to `mid_turn: "queue"` with `queue_evidence: ["Press up to edit queued messages"]` and a new rule field `queue_evidence_placement`, `same_line` (the default, Pi's rule, unchanged) or `later_line`: the first 40 characters of the sent text are on a line that starts with a prompt glyph, and a LATER line of the screen contains an evidence marker. A queued send is recorded as Pi's is (state PANE_STILL_THINKING, submitted true, queued true, note `queued`, exit 0). Without that evidence the result is INPUT_BAR_ONLY, exit 7, note `queue-not-proven`, and no second Enter, as for Pi. The rule is proven on real captures of a Claude Code pane holding a queued message, stored with placeholders for private text and a PROVENANCE entry; without a real capture this part must not ship. Every other harness keeps the bounded wait and refusal. The idle-path shortcut that treats any screen containing the words "queued messages" as processing is narrowed to the same evidence rule.
- B2. Input bar. On Claude Code the input bar is the prompt-glyph line that sits between the two horizontal rule lines above the mode footer. A prompt-glyph line BELOW the footer (the selector of the sub-agent list) is not the input bar: it is never read as stale text and never gets an Enter. Seen live on 2026-11-10: the sender read that selector line as stuck text, pressed Enter and refused with INPUT_BAR_ONLY. Proven on a real capture of that screen. Real captures used by B and B2 (taken 2026-11-10, private originals kept outside this repository): a busy pane before a send, the text typed and not yet entered, the queued state after Enter, and the sub-agent selector screen.
- C. Message digest. Every record written by `say` carries `message_sha256`: the lower-case hex SHA-256 of the UTF-8 bytes of the text exactly as sent to the pane (after the sender's own whitespace flattening). The README states that definition. Records written by `status` and old log lines have no such field and still parse. The digest comes from the `sha2` crate, pinned to an exact version, the only dependency change.
- Validator (TypeScript). `SEND_FAILED` and the already-emitted `PANE_READ_FAILED` are added to the delivery-state and send-refusal-state lists in src/protocol/service.ts, each with verdict not_delivered; both map to no PlanGraph fact in the round-trip test; a Claude Code queued record maps as the Pi queued record does. The golden corpus is regenerated by the real sender flow and gains: a SEND_FAILED record with a transport error, an enter-failed record, a Claude Code queued record, and a read-failed record. Unknown fields stay ignored by the validator; `message_sha256`, when present, must be 64 lower-case hex characters, else the record is invalid.
- The generated baseline manifest for src/protocol is regenerated by its script (own rows only).
