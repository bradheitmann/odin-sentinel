# Done list — registry-lock-async (written BEFORE dispatch; does not grow during it)
Base bytes: 421986c (main)
Problem: the event registry's lock wait (src/protocol/event-registry/storage.ts, acquireRegistryLock) sleeps synchronously (Atomics.wait) for up to its 10 s budget. Today the default MCP server injects no registry store, so its append tool fails closed and never waits. The unlanded branch fix/registry-cli-store-20261020 wires the store into the default server; once that lands, a contended lock would freeze the whole MCP server's event loop for up to the budget (QA finding F2 on registry-lock-budget). This slice is that branch's prerequisite.
Design (fixed for this slice):
- Add an asynchronous lock path in storage.ts (acquireRegistryLockAsync and appendRegistryEventAsync) that uses the same policy (capped exponential backoff with jitter, wall-clock budget, explicit maxLockAttempts/lockRetryMs honoured, same lock_unavailable code and events.lock field on exhaustion) but waits with timers, never blocking the event loop. Share the policy with the synchronous path; do not fork it.
- The registry store seam (GovdispRegistryStoreLike in src/protocol/governance.ts) gains an OPTIONAL async append. The service function used by the MCP tool prefers the async append when the store provides it, and otherwise behaves exactly as today.
- The MCP `odin_append_event` handler awaits the service result. With no store injected (today's default) its output is byte-identical to before.
- The synchronous path, compaction and the CLI stay as they are.
Write scope: src/protocol/event-registry/storage.ts, src/protocol/governance.ts (store seam and append service only), src/mcp/server.ts (odin_append_event handler only), tests/protocol/registry-lock-async.test.ts (new), tests/mcp/ (one new test file for the event-loop proof), tests/fixtures/govdisp/baseline-manifest.json (regenerated by its generator only, per the standing PM ruling). Nothing else.
Proofs (each: name, what it guarantees, reopen step, fail-without mutant):
1. event-loop-free: while another process holds the registry lock for about 2 s, an MCP server whose injected store provides the async append keeps answering a second tool call (for example odin.get_version) in under 300 ms, and the pending append later succeeds once the lock is released.
   - Reopen: `pnpm vitest run tests/mcp/<new test> --testTimeout=30000` from a clean clone of the frozen tip.
   - Fail-without mutant: make the async append call the synchronous acquire; the second call must be delayed past the threshold and the test must go red.
2. same-policy-same-refusal: on a lock that is never released, the async path refuses with the same lock_unavailable code and events.lock field once its budget is spent, writes nothing, and honours lockBudgetMs and the explicit legacy options exactly like the sync path.
   - Reopen: `pnpm vitest run tests/protocol/registry-lock-async.test.ts`.
   - Fail-without mutant: let the async path proceed after the budget without the lock; the test must go red.
3. default-unchanged: with no store injected, odin_append_event returns the same store_unavailable result as on main (byte-identical text); the sync path's existing tests (registry-lock-budget, contention, govdisp-compaction) pass unchanged.
